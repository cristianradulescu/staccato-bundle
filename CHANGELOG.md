# Changelog

All notable changes to this project are documented in this file.

The format is based on Keep a Changelog and this project follows Semantic Versioning.

## [Unreleased]

### Added
- `site:build --drafts` / `--no-drafts`: include or leave out draft pages in any environment. Without either option nothing changes: drafts are left out in `prod` and included in every other environment. `--no-drafts` builds without drafts in `dev`, where template and configuration changes are picked up on every build; in `prod`, Symfony runs with debug off and keeps serving its cached container and templates until `cache:clear --env=prod`.

### Changed
- `PageRenderer` reads the site-wide template variables from `SiteConfig` instead of taking them as arguments, so its methods take only what is specific to the render, plus the optional template name as before: `renderPage(Page $page)`, `renderHome(PaginatedHomeContext $home)`, `renderNotFound()`, `renderRss(array $articles)`, `renderSitemap(array $urls)`; `renderRedirect(Page $page)` is unchanged. Its constructor takes the `SiteConfig` and a new `StylesheetResolver` service, which `SiteBuilder` also takes as a new last constructor argument, so the linked stylesheet file names and the copied files come from one place. Templates receive the same variables with the same values (`siteTitle`, `footerText`, `includeDefaultStyles`, `includeHighlighterStyles` and `stylesheets`; `siteTitle`, `siteDescription`, `baseUrl`, `articles`, `urls` and `generatedAt` in the feeds), and the built site is unchanged. Only code that calls `PageRenderer` or constructs these services itself needs updating; applications using the autowired services are not affected.
- `SiteConfig` normalizes its directories (`contentDirectory`, `buildDirectory`, `assetsDirectory`, `staticDirectory`) when it is constructed, with the same rule as the `staccato` configuration. A `SiteConfig` constructed by hand holds the normalized values (`site/pages/` becomes `site/pages`, `\` becomes `/`, surrounding whitespace is trimmed), and an empty or absolute directory, or one with an empty, `.` or `..` segment, throws an `\InvalidArgumentException` from the constructor (so does a segment ending in `.` or a space, see "Fixed"). Before, such a value was rejected only when `SiteBuilder::build()` ran, with a `\RuntimeException`, and an absolute path such as `/build` was built into `build/` under the project directory. The constructor also applies the configuration's overlap rule: a `buildDirectory` that equals, contains or sits inside `contentDirectory`, `assetsDirectory` or `staticDirectory`, compared ignoring case (see "Fixed"), throws `The SiteConfig "buildDirectory" value "content/build" must not overlap with "contentDirectory" ("content"), because the build directory is removed on every clean build.` Such a `SiteConfig` used to be accepted, and a clean build then removed the part of the source directory inside the build directory, all of it when the build directory was the same directory or contained it. `OutputPathResolver::resolveOutputPath()` and `resolveAliasOutputPath()` apply the same rule to their `$buildDirectory` argument: an absolute build directory is rejected instead of being made relative, and surrounding whitespace is trimmed. They still throw a `\RuntimeException`, now `Invalid build directory "…".` for an empty one too. Applications that configure the bundle under `staccato:` are not affected, and the built site is unchanged.
- `sitemap.xml` no longer lists `/rss.xml`, because a sitemap lists the pages search engines should index and the feed is not one; feed readers still find it through the `<link rel="alternate">` in every page's `<head>`. The homepage listings and every page are listed as before. To keep the feed in the sitemap, override `sitemap.xml.twig` and add it there.
- The bundle requires `symfony/config`, `symfony/filesystem`, `symfony/http-foundation`, `symfony/http-kernel` and `symfony/yaml` `^8.1.11`, the versions that fix their published security advisories, so applications never resolve a vulnerable version of them through the bundle.
- An unquoted date used as a key of an inline front matter map, such as `history: {2021-01-01: created}`, fails the build with `Invalid YAML front matter in "…": Implicit casting of incompatible mapping keys to strings is not supported. Quote your evaluable mapping keys instead`, a side effect of front matter now being parsed with unquoted dates read as dates (see the date fix below). It used to become the string key `2021-01-01`. Quote the key (`{'2021-01-01': created}`) to keep it a string; keys of an indented map are not affected.
- A bare number as the front matter `date`, such as `date: 2021` or `date: 20210827`, fails the build with `Front matter key "date" in "…" must be a date such as 2021-08-27, got 2021.` It was read as a Unix timestamp, so `date: 2021` dated the page 2021 seconds after the epoch: 1970-01-01 in UTC and east of it, 1969-12-31 west of it. A site that used an epoch number must write the date instead, with an offset to keep the same instant (`date: 2023-11-14T22:13:20Z` for `1700000000`). Other values that are not a date, such as `date: 2021.5`, `date: true`, a list or a map, fail with the same message, ending in `got 2021.5`, `got true`, `got a list` or `got a map`; they failed with the misleading `must be a non-empty string.` Dates, quoted or not, are read as before, and an empty or unparseable string still fails with `must be a non-empty string.` or `must be a valid date string.`

### Fixed
- An unquoted front matter date without a UTC offset (`date: 2021-08-27` or `date: 2021-08-27 10:30:00`) is read in PHP's default time zone, like the quoted form, both in `date` and in the keys passed through as `page.meta`, at any depth (`updated: 2026-04-01`, `revisions: [2026-01-15]`). It was read as UTC, so with a default time zone west of UTC the page, the homepage listing, `rss.xml` and `article:published_time` showed the previous day, and so did `{{ page.meta.updated|date('F j, Y') }}`. `page.meta` dates keep their type, a Unix timestamp (an int, or a float when the date has fractional seconds); only the value changes. Dates with an explicit offset are unchanged.
- A front matter `date` with fractional seconds (`date: 2021-08-27 10:00:00.5`) is read like any other date. It failed the build with `Front matter key "date" in "…" must be a non-empty string.`
- Aliases that nest inside a generated file, or inside or around another alias written as an `.html` file, fail the build before the build directory is cleaned, like the other alias conflicts: `/rss.xml` and `/sitemap.xml` (written to `build/rss.xml/index.html` and `build/sitemap.xml/index.html`), anything under `/404.html/`, or `/old.html` together with `/old.html/page/`. They passed validation, and the build then failed halfway through writing, after the previous output had been removed.
- A directory setting (`content_dir`, `build_dir`, `assets_dir`, `static_dir`) with a segment that ends in `.` or a space, and an alias with a segment that ends in `.`, are rejected on every platform. Windows drops trailing periods and spaces from path names, so `build_dir: content.` passed the check that keeps the build directory apart from the sources, and a clean build would have removed the `content` directory there; the alias `/a./` was written to `build/a./index.html`, which on Windows is `build/a/index.html`, so it would have replaced the page `/a/` with a redirect. The configuration now fails with `The "staccato.build_dir" value "content." must be a path relative to the project directory, with no segment that is empty or ends in "." or a space (such as "..").`, a hand-built `SiteConfig` with the same wording (`The SiteConfig "buildDirectory" value …`), `OutputPathResolver`'s `$buildDirectory` argument with `Invalid build directory "…".`, and the build with `Alias "/a./" in "…" may only contain letters, digits, ".", "_", "~" and "-" between slashes, with no segment ending in ".".` The same alias message now also rejects a segment ending in a line break, such as `"/old\n/post/"` in a double-quoted YAML string, which was written to a directory whose name ends in a line break. Dots and spaces elsewhere in a segment are allowed as before (`site/.output`, `v1.2`, `/2020/01/post.html`, `/~user/v1.2/`), and spaces around a whole directory setting are still trimmed. Only sites with such a directory or alias are affected: rename the directory, and remove the alias; a `SiteBuiltEvent` listener can still write a redirect for such an old URL on a build that does not run on Windows (see "Adding files after a build" in the README). Found by reading the code; not reproduced on Windows.
- A `build_dir` that differs from `content_dir`, `assets_dir` or `static_dir` only by case, or that contains or sits inside one of them with only a difference in case, is rejected: `build_dir: Content` next to `content_dir: content` fails with `The "staccato.build_dir" value "Content" must not overlap with "staccato.content_dir" ("content"), because the build directory is removed on every clean build.`, and so does `build_dir: site` next to `static_dir: SITE/static`. The check compared the directories case-sensitively, so these passed, and on a case-insensitive filesystem (the macOS and Windows defaults), where they are the same directory, a clean build would have removed the source directory, or the part of it inside the build directory, after reading the content. The comparison now ignores case on every platform, for letters outside ASCII too (`Über` and `über`), in the `staccato` configuration and in a hand-built `SiteConfig` (see "Changed"). On a case-sensitive filesystem, such as Linux's, these were separate directories and the build worked; it now fails there too, so rename one of the directories. Found by reading the code; not reproduced on macOS or Windows.
- Content file paths use `/` as the separator on every platform. On Windows, Finder returns them with `\`, so articles would have kept the `articles/` prefix in their URL (`/articles/hello/` instead of `/hello/`) and been left out of the homepage listing and `rss.xml`. `Page::$sourcePath`, which `SiteBuiltEvent` listeners also receive, now always uses `/`. Found by reading the code; not reproduced on Windows.
- The bundle requires `ext-dom`. The excerpt of a page without an `excerpt` in its front matter is extracted with `Dom\HTMLDocument`, and nothing else required the extension, so on a PHP without it (Debian and Ubuntu ship it in `php8.5-xml`) the bundle installed and `site:build` then failed with `Class "Dom\HTMLDocument" not found`. `bin/create-blog.sh` checks for it along with `ctype` and `iconv`. `symfony/polyfill-mbstring`, which that excerpt code relies on when `ext-mbstring` is missing, is now a direct dependency instead of coming only through Symfony and Twig. `ext-ctype` and `ext-iconv`, which the bundle does not use, are no longer in its own requirements; `symfony/skeleton` applications still require both.
- In an application created by `bin/create-blog.sh`, `site:build` in `dev` ignored the generated `config/packages/staccato.yaml` and built with the default configuration (a site titled `Staccato`), however often the file was edited, until `cache:clear` was run. Composer's `cache:clear` auto-script builds the `dev` container before the script writes the file, and Symfony's `dev` container only notices changes to the configuration files it was built from, not new ones. The script now removes `var/cache/` after writing the configuration, so the next command builds the container with it; it does not run `cache:clear`, which skips the rebuild when the container was written in the same second it starts. Its first build and the rebuild command it prints are now `site:build --no-drafts` instead of `site:build --env=prod`: the output is the same and the sample draft is still left out, but changes to configuration and templates are picked up on the next build, while `prod` keeps serving its cached ones until `cache:clear --env=prod`. The generated GitHub Pages workflow still builds with `--env=prod`. The README notes the same `cache:clear` for a `config/packages/staccato.yaml` created after `composer require`.

## [0.2.0] - 2026-10-25

### Added
- Layout blocks in the default `base.html.twig`: `head_extra`, `header`, `site_title`, `nav`, `footer` and `footer_content`. Extend `@!Staccato/base.html.twig` and fill in only the blocks you need instead of copying the whole layout. The default theme styles a `<nav class="site-nav">` in the header.
- Social metadata in the default templates: `og:site_name`, `og:type`, `og:title`, `og:description`, `og:url`, `twitter:card`, and `article:published_time` for dated pages. Customizable through the `social_meta`, `og_type`, `og_title` and `og_meta` blocks.
- `static_dir` configuration (default `static/`): its files are copied to the root of the build directory as-is, for `favicon.ico`, `robots.txt`, `CNAME` or `.well-known/`. Static files that would replace or nest inside generated output fail the build before the build directory is cleaned.
- `page.meta` (and `meta` on homepage listing items): every front matter key other than the ones Staccato interprets, passed through untouched, so templates can use `author`, `tags` and similar keys.
- `aliases` front matter: old URLs of a page, each written as a redirect page (`redirect.html.twig`: meta refresh, canonical link, `noindex`). Aliases keep their case and may end in `.html`, so URLs from a previous generator keep working. They are validated against every other output before the build directory is cleaned.
- `Staccato\Event\SiteBuiltEvent`, dispatched after a successful build with the build directory and the built pages, to add files such as redirects, a search index or extra feeds from a listener.
- `site:build` reports the number of static files copied and redirects generated.
- `bin/create-blog.sh` writes a GitHub Pages deployment workflow (`.github/workflows/pages.yml`) and creates a `static/` directory.

### Changed
- `bin/create-blog.sh` requires PHP 8.5 in the generated `composer.json` and removes the web front controller (`public/`, `src/Controller/`, the skeleton's `templates/base.html.twig` and the `assets:install` auto-script), which a static site does not need.
- `SiteBuilder` takes an event dispatcher as a new constructor argument; `symfony/event-dispatcher` is now a direct dependency. Applications using the autowired service are not affected.
- The header container of the default `base.html.twig` has an extra `site-header-inner` class, laid out as a flex row.

## [0.1.0] - 2026-10-24

### Added
- Initial release of `cristianradulescu/staccato-bundle`, a Symfony bundle that turns Markdown content into a static site.
- `Staccato\StaccatoBundle` (`AbstractBundle`) exposing a validated `staccato:` configuration tree: `title`, `base_url`, `description`, `language`, `articles_per_page`, `footer_text`, `include_default_styles`, `stylesheets`, `highlighter_css`, `content_dir`, `build_dir`, `assets_dir`.
- Default templates (`base.html.twig`, `page.html.twig`, `home.html.twig`, `404.html.twig`, `rss.xml.twig`, `sitemap.xml.twig`) shipped under the `@Staccato` Twig namespace, so a site works out of the box with no templates of its own; any single template can be overridden via `templates/bundles/StaccatoBundle/<file>.twig` in the consuming app.
- SEO basics in the default templates: `<html lang>`, meta description (page excerpt or site description), absolute canonical links for pages and paginated home pages, and an RSS alternate link.
- Twig helpers for templates: `staccato_path()` for internal links and assets, `staccato_url()` for absolute URLs, and a `staccato` global exposing the site configuration.
- Sub-path hosting (e.g. GitHub Pages project sites): the path of `base_url` is applied to every internal link and stylesheet.
- A default, dependency-free theme (`public/css/staccato.css`), copied to `build/assets/staccato/staccato.css` on every build. `include_default_styles` toggles it; your own `stylesheets` and a `highlighter_css` code theme are copied and linked independently, so the theme can be extended or replaced through config alone.
- `site:build` console command with `--clean`/`--no-clean` and `--use-fixtures` options, environment-aware draft handling (`dev` includes drafts, `prod` excludes them), and the full exception on `-v`.
- Markdown content loading (`ContentLoader`) with YAML front matter (`title`, `slug`, `date`, `excerpt`, `draft`; tolerant of CRLF line endings, a UTF-8 BOM and trailing whitespace on delimiters), HTML conversion via `tempest/markdown`, syntax highlighting via `tempest/highlight`, and plain-text excerpts derived from the rendered body.
- Directory-style URL/output path resolution (`OutputPathResolver`), with `content/docs.md` mapping to `/docs/`. `index.md` files and slugs resolving to `/` are rejected, since `/` is the generated homepage.
- Build safety: configuration, content, duplicate output paths and pagination conflicts are validated before the build directory is cleaned, so a failing build keeps the previous output.
- Paginated homepage generation from `content/articles/` (`articles_per_page`), plus `404.html`, `rss.xml`, and `sitemap.xml` generation, and static asset mirroring into `build/assets/`.
- Optional Faker-based fixture content generation (`FixtureContentGenerator`) for demoing a site without committing real content; requires the suggested `fakerphp/faker` package.
- `bin/create-blog.sh`, a helper script that creates a new Symfony application with Staccato, sample content and a first build.
- Quality tooling: PHP CS Fixer, PHPStan (level 7), PHPUnit, and a `composer qa` quality gate.
